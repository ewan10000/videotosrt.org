# General audit fixes: rollout and recovery

Changes preserve the price catalog, monthly quotas, credit-pack quantities and successful API response shapes. New session tokens carry `purpose=session`. Ordinary authentication accepts those and the original two-field `{userId, exp}` session format only; it rejects all other purposes, malformed IDs and nonnumeric/expired expirations. Existing genuine sessions need no bulk logout.

## Rollout order

1. Back up the shared D1 database using the established operations procedure.
2. Apply `migrations/0005_checkout_attempts.sql` once to the SAME D1 database used by both billing engines. The frontend copy is `schema/checkout-attempts.sql`; do not create a separate billing database. Existing migrations through 0004 are prerequisites. This additive migration creates only the durable checkout-attempt table/index and leaves legacy locks intact.
3. Apply `migrations/0006_checkout_replay_guard.sql` to the shared D1 database (frontend copy: `schema/checkout-replay-guard.sql`), then `migrations/0007_transcription_execution.sql` for the backend worker. These add a durable replay marker and nullable execution token; existing attempts/jobs remain recoverable.
4. Roll out backend API and queue worker code together, then the identical frontend billing engine. Drain or stop old queue consumers before enabling token-fenced workers, since old consumers can write unconditional completion. Avoid leaving old billing creators running during recovery: old code may replace expired unresolved locks. Billing fails closed if the attempt table is missing.
5. Verify session authentication, quota/ledger consistency and checkout recovery with local or explicitly authorized test environments. No live Stripe calls, deployment or production database writes were made during this change.

## Checkout recovery

Before a Checkout POST, the lock and original URL-encoded parameters are persisted atomically. A retry for the same configured price uses the saved body and `checkout-<attempt>` key, including the original email/customer, expiry, metadata, return URLs and Managed Payments options. Never rebuild parameters for an unresolved attempt. A successful remote creation followed by a local persistence failure follows the same recovery path. Concurrent recovery requests share Stripe's idempotency key and persist the mapping idempotently.

Structured Stripe validation/auth rejections release only a newly created attempt's matching lock when no replay has registered and no session mapping exists. Idempotency errors, key-in-use conflicts and parameter mismatches are always ambiguous, including HTTP 400. Every POST first conditionally registers against the current lock; replay registration permanently bars creator-side release. Release and registration serialize in D1: a stale recoverer whose lock was already released cannot POST. Network/timeout errors, malformed responses, conflicts, rate limits, server errors and local persistence failures retain their locks. Even a later definitive rejection during recovery does not prove that an earlier ambiguous request failed, so that lock stays retained. Different purchases cannot replace unresolved attempts, even after the original 32-minute lock expiry.

Automated POST recovery stops at 23 hours after attempt creation, before Stripe's minimum 24-hour idempotency retention boundary. Unmapped legacy locks have no recoverable request body and remain blocked even when expired. Operators must reconcile those and aged ambiguous attempts with Stripe using authorized tooling: establish whether a session/payment/subscription exists, persist a verified mapping if appropriate, or confirm absence/expiry before conditionally releasing the exact lock attempt. Do not delete a lock merely because its timestamp expired. A durably mapped checkout retains the existing 32-minute expiry behavior.

Attempt bodies contain customer/email information; protect database access and backups, and do not print request bodies or authorization headers in operational logs. Attempts are retained for reconciliation; any later retention cleanup must preserve unresolved attempts.

## Transcription and quota

D1 `batch` is the transaction boundary. Generic debits and idempotent grants update quota and ledger together; transaction failure leaves neither partial debit nor a grant marker that blocks retry. Transcription inserts the job reservation only while quota is available, then debits and records the ledger in the same batch. Only the request that inserted the reservation enqueues it. Duplicate requests return the existing job and its original charged duration.

Queue-send rejection conditionally changes only a still-queued owned job to failed, inserts its unique refund and adjusts the original usage month in one batch. If the consumer has already claimed processing/completed status, the request cannot fail or refund it. Each consumer claims queued/processing jobs with a fresh execution token, allowing redelivery to recover interrupted processing. Every completion and failure checks processing status and that token; later claims fence all older outcomes. Terminal jobs cannot be claimed again. The winning failure transition, unique refund ledger entry and original reservation-month quota adjustment run in one changes()-gated D1 batch. A lost transition produces no refund; refund failure rolls back the transition for retry. Duplicate failed-job refunds remain idempotent. Overlapping deliveries can still call the provider, but only the current execution may publish or refund the result.

D1 and Queue do not share a transaction: process termination after the committed reservation but before send can still strand a queued charged job; failed compensation database writes can also leave a queued job requiring reconciliation. This change does not implement an outbox/reconciler. Inspect stale queued jobs and confirm delivery/processing before refund or resubmission. Existing historical quota/ledger inconsistencies are not automatically repaired.

## Validation

Tests were added and executed before source fixes to reproduce purpose misuse, partial debit/grant failures, forced same-key transcription concurrency, queue acknowledgement loss, definitive checkout rejection, ambiguous creation, local checkout persistence failure and expired legacy lock replacement. Additional regressions force creator/recoverer/third-request interleavings, HTTP 400 idempotency conflicts, completion immediately before the failure transaction, refund rollback, and overlapping opposite worker outcomes. Final validation: `npm test` and `npm run typecheck` in both repositories, plus `git diff --check`. Stripe is mocked and all database fixtures are in-memory SQLite; runtime-specific D1/Queue behavior remains a rollout verification item.
